# Screeps 帝国重构总计划

> **给执行者**：按任务推进，每次先读[续接记录](2026-11-16-empire-refactor-state.md)，再读本文件的全局约束和当前任务。执行阶段使用 `superpowers:executing-plans` 的逐项验证方式（可用时）。复选框只在对应证据落盘后更新。

**状态**：2026-11-16 用户确认以本计划作为目标模式的执行依据。此文件描述完整目标、目标架构、实施依赖、验收和回滚。各阶段的首次生产操作沿用原有授权边界。

**目标**：让帝国能自行维持单房、经营单个远程矿、协调第二个房间，并在此基础上按需扩展工业和防御。每个阶段都能通过真实的投入、动作、结果和恢复证据判定进度。

**架构**：保留 Screeps tick 主循环和现有执行能力，按业务链逐步明确事实、策略、许可、执行与结算边界。短期启用和试点历史通过既有安全协议管理，持久历史按需读取。每次迁移都有对照基线与可回退的执行入口。

**技术栈**：Screeps World JavaScript、`Memory`、Node `node:test`、Rollup。开发使用仓库既有依赖。Screeps MCP 可用于可用的只读观测，游戏内状态与动作回执仍由游戏运行时产生。

**依据**：[原帝国路线图](../specs/2026-06-05-automation-empire-roadmap.md) · [单房生存与恢复](../specs/2026-10-13-single-room-survival-recovery-design.md) · [单远程矿](../specs/2026-10-14-single-remote-mining-design.md) · [能力与架构复评](../evidence/2026-11-16-empire-capabilities-architecture-review.md)

## 目标和验收层次

| 层次 | 帝国应当能完成的行为 | 进度证据 |
| --- | --- | --- |
| 单房自给 | 在普通运转、缺员和能源紧张时，维持采矿、物流、孵化与 Controller，随后恢复非紧急建设和升级 | 实际 Spawn 回执、核心可用能力和供能恢复；原单房同版本 10,000 tick 线上验收仍待完成 |
| 单个远程矿 | 母房支持一处源点的侦察、容器、采集、装货、返程和卸货；必要时撤权并收尾 | 首批同轮同趟新产能量真实入库，下一 tick 对账。首趟净额可为负 |
| 持续远程经营 | 允许自然补员、设施维护和安全暂停，成本与实收可解释 | 实际自然替换、多个完整往返、线上条件允许的真实场景与同版本长窗审阅 |
| 多房协同 | 成熟房能支援指定第二房，第二房建立基本自给；两房仍各有核心能源保底 | 权限和附带费用可核对，补给真实到达，新房有自己的采矿、物流和 Spawn |
| 工业与安全 | 各房按明确需求执行矿物、实验室和必要交易；态势恶化时先保生存 | 每条链各有实际产物或行为回执、预算、失败处理与可逆控制 |

不同层次分别验收。首批真实入库只证明运输链；长期收益还要核对补员、基础设施、成本和安全恢复。阶段完成以游戏行为为准，代码量、回归组数、归档与版本发布作为支持证据。

## 角色能力与系统依赖

| 角色或职责 | 最小能力 | 需要的系统 | 可验收结果 |
| --- | --- | --- | --- |
| 本房矿工 | 合法工位、采集、入本房物流、退场后能补位 | 人口事实、工位、孵化、任务许可、资源交付 | 新矿工能在对应源点实际恢复供能 |
| 本房运输者 | 取货、优先配送、满仓与目标失效处理 | 资源市场、owner 预留、任务执行及结算 | Spawn 等关键目标收到能量，失败只释放原 owner |
| 建造者 | 按工单、合法工位和预算建造 | 城建规划、优先级、物流、工位 | 工地实际推进，核心供能短缺时普通工单暂停 |
| 维修者 | 优先维持经营、防御和通行需要的设施 | 资产状态、维护工单、预算 | 目标耐久实际恢复，维修有效结束 |
| 升级者 | 保护 Controller，按能源水位调整投入 | 房间阶段与恢复、孵化、物流 | 危急时维持必要升级，平时可解释地分配能量 |
| 防御者和塔 | 识别威胁，执行防御与撤退优先级，避免挤占自救 | 情报、安全、任务许可、预算 | 危险时停发不安全任务，防御动作有证据 |
| 侦察者 | 跨房、取得新鲜视野、记录可用路线和威胁、安全返程 | 情报、路径、有限侦察许可 | 同身份跨房、视野、风险、出发／撤回回执 |
| 远程矿工 | 就位、准备或使用容器、采集、卸入远端容器、必要维护 | 远程经营、路线、工位、建筑、费用 | 容器状态与本轮新产能量来源可追踪 |
| 远程运输者 | 绑定一次运输、装货、返程、指定母房卸货、收尾 | 经营许可、路线、预留与次 tick 结算 | 同一趟运输在母房确认实收，撤权后按许可处理余货 |
| 矿物工与工业运输 | 从已许可矿点采集，按批次运料、清除污染和回收产物 | 库存保底、工单、Lab 计划、物流 | 可核对初始材料、实际消耗、产物与剩余 |
| 开拓者、先遣工和支援运输 | 占领指定房间，建设 Spawn，供能直到新房自给 | 目标计划、候选评分、GCL／预算、跨房物流 | 逐段验收 claim、Spawn、基础自给以及支援撤出 |

角色表定义职责。一个策略可以承担多种职责，单位数量由有效能力、行程和预算推导。现有矿工、运输者、建造者、维修者、升级者、防御者和远程角色先按行为对照，实施时复用已验证的策略。

## 目标架构与权责

下表是目标接口和数据归属。字段描述需要明确传递的事实，具体文件和函数随阶段设计落地。

| 边界 | 接收 | 输出及写入者 | 现有落点 |
| --- | --- | --- | --- |
| 当前事实 | Game、必要的存量状态与当前 tick | 房间、库存、可用角色、待孵化、路径与威胁、证据来源和新鲜度；采集者只读 | RoomCache、CreepPopulation、RoomPhase、各 Facts 模块 |
| 策略与优先级 | 明确事实、Policy、上一次有权推进的状态 | 缺口、合法工作、预算建议、原因；影子结果只在影子命名空间 | RoomGovernorModel、SpawnBureau、规划与经营纯模型 |
| 经营与许可 | 当前事实、经营状态、配置、独立批准的试点权限 | 身份、动作、允许范围、期限、停因；经营状态由归属服务推进，试点守卫负责接纳与撤权 | RemoteMining、RemoteEconomicTrial、NativeEconomicTrialOps |
| 行为意图与执行 | 角色、已批准的工作和有效许可 | 受约束的 Spawn／Task 意图及一次原始结果；各执行器只写其动作回执 | SpawnBureau、SpawnService、TaskGuard、策略、ActionParser |
| 预留与结算 | 原身份、预留 owner、动作与次 tick 双边事实 | 实收、支出、unknown、释放或到期；资源预留和账目由各有权归约器写入 | ResourceMarket、ResourceReservationFeedback、RemoteMiningLedger |
| 历史与观测 | 持久回执、运行状态、只读 Game 事实 | 有版本、来源、时效的摘要与封存记录，历史按需核验 | RuntimeTelemetry、EmpireMetrics、证据窗口、Screeps MCP |
| 战略与目标 | 各房经营事实、可用预算和人工目标 | 候选方案、优先级、预算请求、明确完成条件；先影子对照 | Goal/Plan、RoomGovernor、后续 EmpireDirector |

一个 tick 的逻辑顺序为「收集事实 → 算出健康、权限和需求 → 仲裁孵化／预留及选任务 → 执行动作并记回执 → 用后续事实结算 → 输出摘要」。迁移时保留现有 `init/analyze/dispatch/run/ActionParser/cleanup` 时序，通过小范围适配逐步明确依赖。拒绝让影子、看板和历史归档发出业务动作。安全检查可以依赖当 tick 核运行态，它需要的持久回执只读其有权核对的范围。

- **当 tick 数据**带 `Game.time`、来源及新鲜度。缺失和过期保留为显式状态。旧缓存不能成为新的安全凭证。
- **跨 tick 业务状态**按房间、经营对象、会话和执行身份区分。有权写入者明确，计划中的能力、已接纳与存活能力分别记录。
- **动作回执与预留**可按原身份恢复。游戏 API `OK` 标为动作已接受，实收用下一 tick 的库存变化与来源对账。无法归因留作 unknown。未知写入使用原身份读回，禁止自动重放。
- **审计记录**保留旧档案和停因，明确格式版本。活动路径只消费履约与授权所需的证据。现有线上 `07/09/10` 和四份旧档案完整保留。

5. 每个改变行为的任务先冻结旧行为或复现问题，再写可判定的回归。离线对照通过后才进入构建、关闭态发布验收、独立的线上启用和验收。发布与启用是不同状态。
6. 相同输入只允许一个执行路径写动作或业务状态。影子和新格式读回共存期间由旧执行路径保持生产权。回滚前先核对旧代码能否读新状态。无法完整读回时，先关闭相关新能力并保留线上原证据，再按具体迁移方案处理。
7. 真实观测记录仓库提交、运行版本、世界和房间、Game tick／窗口、行为样本和缺测。旧版本样本可以作为比较，不能拼作新版本验收。CPU、bucket、遥测和 Memory 分开报告。
8. 验收用的具体业务事件必须出现才标通过。隔离回放覆盖危险、损坏、超期、重置和未知；线上缺失的场景单独记未覆盖。试点关停、新鲜预检及明确授权按原定义执行。

优先复查五类失败：旧回执和超期回执、缺失或过期的事实、并发预留与重复执行、重置或写入结果不明、版本和账目跨会话污染。每条链用能够触发真实入口的回归验证。

### P7 工业、高级设施和常态优化

- [ ] **P7.1** P2 通过后设计单房矿物链。验收采集、到指定库存、所有权、耗时、满仓撤单。用同样的库存和物流协议接一个 Lab 批次，验证耗料、污染清理、产物、恢复及取消。
- [ ] **P7.2** 按 RCL、设备、库存和已批准业务范围扩展 Terminal、市场、Factory、Power 等。每种能力先一房、一种资源或配方、一个预算，分别验收真实回执和安全停止。交易和生产保持独立的权限边界。
