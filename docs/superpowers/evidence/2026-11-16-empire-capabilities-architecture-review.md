# Screeps 帝国能力与架构复评

2026-11-16。此稿用于决定重构方向。代码盘点基线为 `codex/single-remote-mining` 的 `8399eac`，与本地 `main` 分开评估。游戏结果引用既有证据；现况以今后独立的线上验收为准。

## 我们要建成什么

帝国先维持母房的基本经济、补员和恢复，再用一条可持续的跨房物流验证扩展能力。多房协同的第一件事是成熟房能按预算支援另一房，直到新房自给。要能看清每个业务为何运行、卡在哪里、支出是多少、确实完成了什么动作。原路线图依次描述了房间稳定、远程经济、工业及多房扩张，适合作为长期能力索引。

| 阶段 | 最小验收情景 | 当前证据 |
| --- | --- | --- |
| 单房稳定 | 原矿工退场或关键运输者缺失时，系统优先补齐核心能力并恢复供能；Controller 安全；建设与升级的能量使用仍有优先级 | 单房恢复能力已部署；原定 10,000 tick 真实验收仍待完成 |
| 单远程矿 | 一处源点完成侦察、容器准备、采集、装货、返程及指定收货点次 tick 确认；超出安全条件时停派并支持受控收尾 | 09 与 10 有视野、100 连续安全 tick、矿工施工及关停证据；确认入库为 0 |
| 可持续经营 | 在途货物结算、角色自然替换、容器维护和预算暂停；按真实 delivered 与费用核算长期收益 | 有本地覆盖和部分线上证据，仍缺完整线上闭环 |
| 多房协同 | 成熟房在保住核心岗位与库存的前提下支援指定第二房，第二房建立基本自给 | 路线图能力，需单独验收 |

首趟真实入库是一项里程碑，允许净值为负。自动建容器与首趟运输分别有证据，长期净收益是后续里程碑。连续运行时长、异常覆盖和业务结果分别定验收条件。

## 角色和系统需要承担的能力

| 角色 | 要负责的行为 | 完成或退出的证据 |
| --- | --- | --- |
| 本房矿工 | 取得合法工位，采集并交给本房物流；失位或补员后恢复 | 工位占用、产出进入物流、有效 WORK 恢复 |
| 本房运输者 | 按优先级取货和配送，保证 Spawn 等关键目标优先供能 | 实际库存变化；满仓、目标消失和任务取消按 owner 释放 |
| 建造者、维修者 | 完成批准的工地和维护任务，能量紧缺时让出预算 | 工地进度／耐久变化、任务结束或被安全撤销 |
| 升级者、防御者 | 维持 Controller 安全，威胁或紧缺时受房间优先级约束 | Controller 和威胁状态改变时，实际任务随之改变 |
| 侦察者 | 取得目标视野与路线事实，撤权后安全返程 | 有时效的情报、真实跨房及返程位置 |
| 远程矿工 | 就位、建设／维护容器、采集并向指定容器交付 | 同身份 BUILD 与产出、容器实际变化 |
| 远程运输者 | 绑定同趟装货、返程、卸货，撤权后按许可收尾 | 母房目标次 tick 确认、预留释放、费用按轮归属 |
| 开拓及房间支援角色 | 占领、孵化支持、运送物资并建立新房基本经济 | 指定第二房在约定资源范围内从启动走到自给 |

这些角色是职责清单。代码中的同一套 body 或策略可以承担多个职责。孵化由能力需求和房间阶段决定，人数不是能力的唯一度量。

| 系统 | 当前实现入口 | 重构后明确的职责 |
| --- | --- | --- |
| 房间事实、健康与政策 | RoomCache、RoomPhase、CreepPopulation、RoomGovernor | 输出带 Game tick 的当前事实；健康与优先级由明确策略计算，影子建议单独记录 |
| 孵化 | SpawnBureau、SpawnService | 对照有效能力与缺口，决定配额和优先级；区分规划、待接纳、已接纳和存活；记录一次执行的回执 |
| 任务执行 | 各角色策略、TaskGuard、ActionParser | 策略从已授权工作中选下一步，执行前校验许可，动作产生可归属的执行结果 |
| 物流与结算 | ResourceMarket、ResourceReservationFeedback、RemoteMiningLedger | 预留、到期释放和确认收支有明确写入者；保留 owner、trip、动作和次 tick 证据 |
| 建设维护与防御 | CityPlanner、MaintenancePlanner、RoadPlanner、Security、TowerDefense | 规划产生工单和优先级，有相应角色和预算消费工单；关键防御可限制普通经营 |
| 远程经营 | RemoteMiningState、RemoteMiningService、RemoteMiningStrategy | 管理经营对象、安全、预算意图、补员和受控返程，有一份权威的经营状态 |
| 试点与观测 | RemoteReconTrial、RemoteEconomicTrial、NativeEconomicTrialOps、RuntimeTelemetry、证据窗口、MCP | 把一次性接纳、撤权、审计和历史归档的职责写清凭证与读取边界；观测报告反映证据新鲜度，游戏内守卫负责实时安全 |
| 长期统筹 | Goal/Plan、Governor 影子能力 | 当各经营环节有可靠事实后，再比较方案、分配跨房资源和决定是否扩张 |

## 原架构与今天的偏差

最初采用按 tick 运行的服务链，使用 `Memory` 保存跨 tick 状态，角色策略选择任务，执行器调用游戏 API。原远程设计复用 SpawnBureau、ResourceMarket 和已有任务执行器。RoomGovernor、Goal/Plan 及若干经营状态已经提供了事实收集与纯计算分离的范例，这部分应当保留。

目前在 `src/main.js` 注册了 37 个服务。静态扫描 `src` 中排除 tests 的 105 个 JavaScript 文件，识别了 324 条相对路径静态导入，未发现多模块静态导入环。这个扫描只统计了能解析到同目录树文件的 `from` 导入。实际耦合还包括 `global`、Memory 共享写入和 analyze、run、cleanup 的顺序。本地分支相对 `main` 多 40 个提交，`src` 差异包含测试和历史夹具，这些数字用于定位审查范围。

| 需要复评的边界 | 源码或真实结果 | 对重构的影响 |
| --- | --- | --- |
| 隐式时序 | 主循环按全体 init、analyze、事件分发、run、动作执行、cleanup 推进。SpawnBureau 同时消费 RoomPhase、Governor 与远程需求；Governor 在另一阶段读取 Bureau 结果 | 阐明事实在哪个阶段有效，固定低成本的跨模块输入和回执，保留已验证的阶段顺序 |
| 试点耦合到经营链 | SpawnService 导入试点接纳函数，ResourceMarket 导入试点结算函数，ActionParser 也检查试点许可。Native 接续依赖历史档案与确权状态 | 经营、任务执行、结算只依赖明确的许可和回执接口；试点适配现有的经营许可，封存史按需验证 |
| 协议进展盖过业务进展 | 09 漏读施工回执后提前退出；10 因常规观察中的预留读取超时退出，两轮均未走到运输者孵化。其后的修复主要让下一轮能安全开始 | 把容器、生产、装货、入库逐项验收。观测通道的失败处理应与它承担的安全职责匹配 |
| 事实、运行状态与历史的寿命不同 | 当前建筑／库存／单位事实随 tick 变化，经营状态需跨 tick，旧试点证据要求可读、可校验 | 给三者分别明确写入者和保留规则；保留 07、09、10 和四份旧档案，既有权限与期限按旧协议验收 |

## 重构路线建议

可以围绕现有主循环逐条提取边界，每一步有旧行为对照和独立回滚。也可以创建一套并行新内核作为离线比较，但在两套调度、状态及结算同时上线前，迁移和一致性成本更高。建议以第一条为主，影子对照作为验证手段。更换架构的完成条件应落在游戏行为和安全边界上，例如同样人口和能源事实下产生同样优先级的补员结果，重置后同一执行回执不重复结算。

首个实践范围建议限定为 W49N41 的「核心补员 → Spawn 接纳 → 恢复供能」。先画清 `CreepPopulation → RoomPhase → SpawnBureau → SpawnService → 回执` 中谁产出事实、谁选择优先级、谁推进状态、谁写 Memory。录下健康与核心缺员两条旧行为，覆盖出生、死亡、补员中和未知回执。接着在影子路径里用明确输入重放，比较补员建议、关键能源优先级和实际执行数。既有单房行为稳定后，可以复用相同方式梳理远程许可和收支，再验证单矿的下一条业务验收。

需要先拍板的范围是「以单房核心恢复做第一条重构路径」以及「哪些状态由实施中的唯一写入者管理」。这份复评作为范围决策材料，具体迁移方案应列出旧、新接口和可回滚边界后再进入实现。
